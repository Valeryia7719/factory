# Design

## Context

The CRM has no data yet. The dashboard is the reference for a feature that crosses the stack: a Drizzle table, a read port, a Pothos resource guarded by `viewerRequired`, the generated `contracts/schema.graphql`, a UI hook that validates the answer with zod, a page with a failure notice, and end-to-end tests that cite scenario IDs. This change copies that shape for contacts. It is the first CRM table, so everything later (companies, deals, notes) can hang off it. Motivation is in the issue.

Nothing can create a contact until issue #2, and the end-to-end suite is black-box and may not open the database, so a populated list cannot be reached end to end yet.

## Goals / Non-Goals

**Goals:**
- A `contacts` table (id, name, email, created and updated dates) with an expand-only migration.
- A `contacts` query for signed-in users, newest first, refused with `UNAUTHENTICATED` otherwise.
- A "Contacts" navigation link and a `/contacts` page listing each contact's name and email, with "No contacts yet." when there are none and a "Couldn't load contacts." notice with a Reload button when the query fails.

**Non-Goals:**
- Adding, editing, deleting, sorting, searching or paging contacts (later issues).
- A unique email, a link to companies, or any seed data.
- Per-user ownership: every signed-in user sees the same contacts.

## Approaches

- **A. Real data in service tests, empty state end to end (chosen).** Backend integration tests and UI integration tests (faked API) cover the populated list; end-to-end tests cover the empty state and the signed-out refusal. The populated-list scenario carries a `NO E2E` line saying a contact cannot be created until #2.
- **B. `bin/seed` adds demo contacts.** Gives a populated end-to-end scenario, but the suite could then never see "No contacts yet.", and demo data would have to be kept in step with later issues.
- **C. The end-to-end suite inserts rows directly in Postgres.** Rejected: the e2e rules forbid opening another service's database.

## Decisions

- **Agent's call: ordering.** Newest first by `created_at`, ties broken by `id` descending, so the order is stable.
- **Agent's call: id type.** A `uuid` primary key generated by Postgres (`gen_random_uuid()`), exposed as the GraphQL `ID`. It keeps ids unguessable and needs no new dependency.
- **Agent's call: layering mirrors the dashboard.** A `ContactStore` port in `src/contacts.ts`, a Drizzle implementation in `src/db/contacts-store.ts`, put on the GraphQL context beside `userStats`, and a resource in `src/graphql/resources/contacts.ts` defining the `Contact` type and the `contacts` root field. The schema module imports it; `bin/contracts generate` regenerates the SDL.
- **Agent's call: dates.** The `Contact` type exposes `createdAt` as an ISO-8601 string; the page does not show it yet.
- **Agent's call: UI.** `pages/contacts/ContactsPage.tsx`, a `useContacts` hook with a zod-validated answer, `services/graphql/contacts.ts` for the query document, a `/contacts` route inside the signed-in layout, a `nav.contacts` link in `AppHeader`, and `contacts.*` keys in `i18n/locales/en/common.json`. Failure behaves like the dashboard: a notice with a Reload button.
- **Agent's call: specs.** A new `contacts` capability spec (the query, the signed-out refusal, the list page, the empty state, the failure notice) and an `app-shell` delta for the navigation link and route. The touched area of `contacts` has no code yet, so no baseline is needed.
- **Tests.** Backend: integration tests for the query (ordering, empty, `UNAUTHENTICATED`) and the store. UI: integration tests for the page states and the route. End to end: the empty state in the browser, the API's empty list for a signed-in client, and the signed-out refusal. No new dependencies.

## Risks / Trade-offs

- The populated list is proven end to end only once #2 can create contacts; until then it rests on service tests. Issue #2's change should add that end-to-end scenario.
- The query returns every contact with no paging. Fine for a starter CRM; paging is a later change.
- A non-unique email allows duplicates until a later issue decides otherwise.
